# 会话前台响应与后台任务：实现计划

[返回文档导航](../../README.md) | [目标规格](../../specs/conversation-foreground-background-model.md)

本目录把目标规格第 14 节的实现顺序拆为 9 个可独立验收的阶段。阶段 01—04 已实现，其余阶段待实现；
各阶段状态及实际入口以对应文档为准，尚未实现阶段中的类型和文件名属于实施建议。目标语义以规格为准，
分层、文件规模和依赖方向以[应用架构](../../architecture.md)为准。

## 执行规则

1. 每阶段按“实现步骤”完成相应代码和定向测试，满足退出条件再推进；阶段 09 汇总与补齐
   系统验收，不能把事务、恢复或状态机测试全部推迟到最后。
2. 阶段 01—06 可用构造函数注入的 fake、临时新数据库和测试 harness 验证。阶段 03 的
   `enqueue` 通过调度契约测试；真实后台入口在阶段 07 接通。未具备执行和终态能力前，
   不对用户开放只接受任务却不能完成的入口。
3. 任务、回执、进度、审批和终态的事务边界先完成，再接入对应行为。内存队列或 ViewModel
   Map 只能帮助调度/渲染，不能作为任务事实源。
4. 从新 schema 开始开发和测试，不增加迁移、旧记录回填、双读或兼容 DTO。开发测试中的
   数据库重建应限定在明确的本地测试数据范围；用户旧数据导出不属于本计划。
5. 隐私净化、验证作用域、消息幂等和副作用对账是各阶段退出条件，不能留作上线后的补丁。
6. 本目录是尚未完成的实施拆分。落地后按 docs 维护规则，把长期约束和实际路径同步到规格、
   架构及实现参考，实施记录交由 Issue、PR 和 Git 历史保存，随后移除已完成的过程文档并修复链接。

## 跨阶段不变量

| 边界 | 必须一直成立的约束 | 主要负责阶段 |
| --- | --- | --- |
| 输入与任务身份 | 同一输入保留 `originTurnId`；重复接受不新增用户消息、任务或回执 | 01—03 |
| 任务接受 | 任务、初始计划/事件与 `taskId:ack` 同事务，提交后才通知和入队 | 02、03 |
| 进度事实 | 事件、工具/审批变化、检查点和物化投影按事件需要在同一事务更新；查询同一快照 | 02、04、05 |
| 执行所有权 | 只有有效 lease 持有者推进执行；用户命令先持久化，旧 runner 不得覆盖新 revision | 02、05 |
| 无整体超时 | 分段预算与单次超时有界；审批、退避和分段切换不构成任务总 deadline | 04、05 |
| 验证与终态 | 接受时冻结验证策略；证据可跨分段但不跨任务；终态与 `taskId:result` 原子提交一次 | 01、06 |
| 前后台分离 | 后台不占前台输入锁；任务脱离页面生命周期；后续普通聊天不修改任务目标 | 03、05、07 |
| 安全展示 | 回执、进度和终态基于净化事实；不保存完整 reasoning、密钥或无限工具输出 | 所有阶段 |

## 验收追踪入口

- 行为基线：目标规格第 15.1 节，由各阶段定向测试覆盖，阶段 09 汇总。
- 故障基线：目标规格第 15.2 节，主要落在阶段 02、05、06，并在阶段 09 验证重启闭环。
- 分层与 UI 基线：目标规格第 15.3 节，贯穿各阶段，阶段 07 完成交互验证。
- 指标基线：目标规格第 13.2 节，随事实写入、前台请求、runner 和 UI 接入埋点，阶段 09 核对。
