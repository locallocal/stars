目标：用行为、持久恢复和用户交互的完整证据确认实现满足规格，再把实际代码路径写回维护文档。

## 行为验收矩阵

| 规格第 15.1 节场景 | 主要负责阶段 | 本阶段核对结果 |
| --- | --- | --- |
| 简单问候、可直接回答的问题 | 03 | 一个主回复模型回合，一个完整直接回复，无任务/工具调用 |
| 长任务、不合格回执草稿 | 02、03、07 | 回执正确或安全兜底，与任务原子保存，接受后输入可用 |
| 后台进行中继续聊天 | 05、07 | 前台正常响应，后台任务目标与执行不受影响 |
| 单任务查询、状态润色、润色不合格 | 02、07 | 一致快照卡片先显示，润色只表达事实，最多修复一次后确定性回退 |
| 多个活动任务 | 02、07 | 返回可区分的任务，不猜测选中哪个任务 |
| 工具调用推进、等待审批 | 02、04、05、07 | 调用前后和审批决定持久化，重启可查可审批，等待不占槽位 |
| 后台中间文本 | 04、06、07 | 无 partial 普通助手结果，只有一个终态结果消息 |
| 旧前台限制、新后台分段限制、超过旧总时限 | 04、05 | 使用新分段预算，有进展则继续，不产生任务 timedOut |
| 单次调用超时 | 04、05 | 保存尝试结果并按策略恢复，不直接因单次超时终结任务 |
| 严格验证成功与失败 | 06 | 同任务有效证据支撑声明，未验证关键声明被抑制 |
| 不可恢复失败、终态润色不可用 | 06 | 安全失败摘要与友好终态回复原子提交，模型失败即时兜底 |
| 用户取消、不可回滚影响 | 05、06、07 | 先取消请求，再停止/对账，唯一取消回复如实说明影响 |

## 崩溃与幂等矩阵

使用可注入故障点、真实临时新数据库和可记录外部调用的 fake；重启时重建 repository、runner、
scheduler 和 Provider session，不能沿用旧内存对象来证明恢复。每项覆盖提交前和提交后的状态。

| 故障点 | 必须证明的结果 |
| --- | --- |
| 任务与回执事务前后 | 未提交则整体不存在；已提交则可扫描恢复；重复输入不产生第二任务/回执 |
| 工具请求发出前、发出后但结果未保存 | 已有调用意图；只读/幂等可安全重试，写操作先对账 |
| 外部 job 创建后、句柄落库前后 | 能找回既有 job 或明确等待确认，不盲目再次创建 |
| 检查点保存前后 | 只从已提交边界恢复，计划、进度和证据游标一致 |
| 最终消息保存前后 | 要么尚未终态，要么消息与状态同时存在；通知/重试不产生第二条结果 |
| 用户取消写入前后 | 已提交取消请求不会丢失，对账完成前不声称已取消；终态竞争只提交一次 |

额外覆盖 lease 过期接管与旧回调、审批决定与恢复之间崩溃、投影损坏重建、多个会话并发、
退避期间重启和页面生命周期变化。所有恢复结果应能从数据库解释为继续、等待或安全终态。

## 分层与交互验证

1. Domain：覆盖状态机、执行策略边界、退避、无进展检测、跨任务证据拒绝、回执/状态/终态事实约束。
2. Repository：覆盖新建 schema、事务回滚、唯一键、revision 冲突、lease、快照查询和投影重建。
3. ViewModel：覆盖后台更新不影响前台 typing、重入读取、过期润色结果拒绝和任务命令错误呈现。
4. Widget：覆盖任务卡片、所有等待/终态、键盘操作、屏幕阅读语义及不同宽度。
5. 集成：使用完整依赖组合，串联接受 → 分段 → 审批/job → 重启 → 验证 → 唯一终态 → 页面重入。
   对后台活跃期间的新直接回复与任务状态查询也做完整验证。
6. 安全与指标：抽查持久记录、日志和导出边界，不含凭据、完整 reasoning、原始敏感参数或
   无限工具输出；按规格第 13.2 节核对延迟、等待、分段/恢复/重试、无进展/对账失败、证据覆盖
   和回退比例。回执可见但任务未创建的指标必须为零。

测试入口按 `test/domain/`、`test/data/`、`test/ui/`、`test/widget/` 镜像组织，共享 fake、clock 和
故障注入 harness 放在 `test/support/`；遵守架构文档的文件规模限制。

## 检查与文档同步顺序

1. 运行各阶段受影响的定向测试，补齐上面的行为与故障矩阵。新建测试文件名按实际实现确定，
   在提交说明中记录运行命令与结果。
2. 运行格式检查、`flutter analyze` 和 `flutter test test/architecture/`，再完成项目完整
   `flutter test` 回归。通过 fake clock 验证长时任务和退避，不用真实等待替代可重复测试。
3. 检查新建数据库下的实际用户流程及目标平台行为，明确进程被系统挂起时的恢复语义。
   有真实运行环境才能标记对应平台通过，不能用单元测试推断所有平台已验收。
4. 更新[用户消息到智能体回复的现有流转](../../reference/user-message-agent-response-flow.md)：
   写入实际 dispatcher、任务接受、分段调度、恢复、状态查询和终态路径，替换旧 run 时序。
5. 同步[事实依据与防幻觉协议](../../reference/conversation-loop-grounding.md)的任务证据作用域、
   策略快照和操作消息信任语义；按需更新[应用架构](../../architecture.md)和 docs 导航。
6. 对照代码更新[目标规格](../../specs/conversation-foreground-background-model.md)的实现状态。
   长期边界保留在规格/参考中，完成记录转入 PR 或 Issue；移除已完成过程文档时同步所有链接。
